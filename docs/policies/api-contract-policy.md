# API Contract Policy

This policy governs API contract maintenance in `devflow-service`.

## Source Of Truth

- `api/openapi/meta-service.yaml`
- `api/openapi/network-service.yaml`
- `api/openapi/config-service.yaml`
- `api/openapi/release-service.yaml`
- `api/openapi/runtime-service.yaml`

These service-scoped files are the canonical shared-ingress frontend/backend HTTP contracts in this repo.
- handler code, route registration, DTOs, domain enums, and middleware remain the implementation authority used to keep that contract honest.
- `api/openapi/devflow.yaml` is the aggregate shared-ingress view.
- `api/openapi/swagger.yaml` and `swagger.json` are generated annotation snapshots; they are secondary proof surfaces, not the primary contract source.

## Required Sync Surface

Any change touching API-related code must re-check and, when needed, update the affected service OpenAPI file and the aggregate `api/openapi/devflow.yaml`.

API-related code includes:

- route registration
- HTTP handler behavior
- request DTOs
- response DTOs
- domain enums
- error envelope or error-code mapping
- pagination shape
- auth middleware
- request_id middleware

## Hard Rules

1. Do not document endpoints that are not registered in code.
2. Do not silently remove documented endpoints unless code has removed them.
3. Paths, path params, query params, request bodies, response bodies, error responses, and enum values must match current code.
4. When code and the old OpenAPI disagree, update the contract to match code and record non-backward-compatible drift in `docs/api/breaking-changes.md`.
5. Uncertain or inferred details must be called out in Assumptions.
6. After API contract work, run `make openapi-check`.
7. Keep each service file aligned to its real ingress-exposed service boundary.
8. If annotation-backed `swagger.yaml` exists, keep the edge-facing contracts semantically aligned with the generated backend-local snapshot plus the ingress routing rules.

## Middleware Contract Notes

- `X-Request-Id` and `X-Request-ID` are echoed or generated by router middleware and should be documented as response headers.
- observer-protected routes accept either `X-Devflow-Observer-Token` or `X-Devflow-Verify-Token`.
- unauthorized observer-token failures return the shared `httpx.ErrorResponse` envelope with code `unauthorized`.
- ingress-facing paths must use the service prefixes defined by `docs/system/ingress-routing.md`: `meta`, `config`, `network`, `release`, and `runtime`
